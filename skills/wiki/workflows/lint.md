# Lint 工作流

对知识库进行健康检查，发现问题并提供修复建议。

> 路径约定：本文档中的 `raw/`、`wiki/` 均指当前知识库的绝对路径，由 SKILL.md 路由时确定（`KB_RAW`、`KB_WIKI`）。

## 语言分工

- `UI_LANG`：面向用户的检查报告、确认问题、修复结果说明使用该语言。
- `KB_LANG`：写入或更新到 wiki 的内容、tags、index、overview、conventions、log 使用该语言。
- lint 不自动翻译旧页面；只能报告语言不一致，并在用户确认后按 `KB_LANG` 处理指定页面。
- 确定性脚本的 JSON 输出属于内部数据，不直接原样展示；需要用 `UI_LANG` 转述为用户可读报告。
- 下方中文模板只表示结构。实际报告按 `UI_LANG` 自然生成，实际写入 wiki 按 `KB_LANG` 自然生成。

## 工作流程

### 1. 运行确定性检查脚本

首先运行：

```bash
python <skill-dir>/scripts/lint.py --wiki-dir <KB_WIKI> --raw-dir <KB_RAW> --json
```

获取脚本检测到的结构性问题。脚本覆盖以下确定性检查：

- 断链（`[[link]]` 指向不存在的页面）。
- `[[raw/...]]` wikilink 误用（应使用普通 Markdown 链接）。
- Frontmatter 完整性（必填字段、type 合法性）。
- index.md 与实际文件一致性。
- 双向链接完整性（A→B 则 B→A）。
- 孤岛页面。
- entity/concept 页面缺少 sources 字段。

将脚本 JSON 输出作为 P0/P1 问题的基础，用 `UI_LANG` 转述；不要把内部 JSON 直接贴给用户，也不要重复检查脚本已覆盖的项目。

### 2. LLM 补充检查

在脚本结果基础上，用 LLM 能力补充脚本无法检测的语义问题：

#### P1 - 质量（LLM 补充）

- **语言一致性**：按 `KB_LANG` 检查每个页面的主体内容是否使用目标语言。只列出不一致页面和建议，不自动翻译；如用户确认，再逐页翻译或修订，保留 frontmatter 结构和 `[[链接]]`。
- **矛盾检测**：扫描所有矛盾标记，汇总当前已知矛盾；同时检查不同页面间是否有未标记的互相矛盾陈述。
- **缺失页面**：被 3 次以上 `[[引用]]` 但没有独立页面的概念/实体。
- **陈旧信息**：updated 日期超过 30 天且有更新素材引用同一主题的页面。
- **空白区块**：页面中有“待补充”、placeholder 或空章节。

#### P2 - 建议（LLM 补充）

- **缺失交叉引用**：内容相关但没有互相链接的页面。
- **标签不一致**：同一概念使用了不同的标签名；只建议统一方向，不迁移旧标签，除非用户确认。
- **可合并页面**：内容高度重叠的页面。
- **新页面建议**：基于现有内容，建议创建的新概念/实体页。
- **数据空白与知识扩展**（使用 WebSearch 工具）：
  1. 识别知识库中明显的信息缺口（如被多个页面引用但缺乏深度的主题）。
  2. 使用 WebSearch 工具搜索相关领域的最新进展、关键论文、权威资源。
  3. 输出建议列表，每条包含：缺口描述、搜索到的推荐来源（标题+链接）、建议的收录优先级。

### 3. 生成报告

输出结构化检查报告，使用 `UI_LANG`。以下模板仅表示结构：

```markdown
## Wiki 健康检查报告 (YYYY-MM-DD)

### 统计
- 总页面数: N
- 素材摘要: N
- 实体页面: N
- 概念页面: N
- 分析页面: N

### P0 - 需要修复
- [ ] 问题描述 → 修复方案

### P1 - 建议改进
- [ ] 问题描述 → 改进方案

### P2 - 可选优化
- [ ] 建议描述
```

报告中的脚本问题需由内部 JSON 转成人类可读描述；保留必要路径、页面名和问题级别。

### 4. 执行修复

向用户展示报告后：

- P0 问题建议立即修复，请求用户确认。
- P1 问题逐项确认。
- P2 问题仅作建议。

用户确认后执行修复：

- 文件内容、frontmatter、tags、index、overview、log 的新增文本按 `KB_LANG`。
- 修复结果报告按 `UI_LANG`。
- 不自动翻译与本次确认无关的旧页面。

## 注意事项

- Lint 操作不会删除任何页面，只会建议合并或更新。
- 如果问题数量很多，分批展示，避免信息过载。
- 每次 lint 后如有实际修复，在 `log.md` 记录检查和修复摘要；只检查不修改时可按用户偏好决定是否记录。
